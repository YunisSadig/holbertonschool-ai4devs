# Reflection - Translating a Log Analyzer into Three Languages

The most useful lesson from this project is that translating code is mostly about agreeing on behavior, not about syntax. The algorithm itself, counting lines, grouping by status and sorting IP addresses, took very little code. Making Python, JavaScript and Java print exactly the same bytes took much more care, and most of that care went into details I would not have thought about at the start.

Writing the specification first paid off. Because it fixed the sort order, the rounding rule and the output format, I could build the implementations against clear rules instead of guessing. I also checked the expected test outputs with a separate Node.js reference before using them, so the tests were not just echoing one implementation. Comparing the three programs byte for byte, instead of comparing parsed values, exposed real bugs that I would otherwise have missed. On Windows the Python program printed carriage returns before every line break, which made its output different from the others. JavaScript's `\S` matched differently from Python's because it understands Unicode, so I had to spell out the character class. Python's `round` rounds half to even, so the spec uses integer arithmetic instead. Java printed small decimals in scientific notation, which led me to use `BigDecimal`. Even Git changed my test data: with automatic line-ending conversion, a fixture that deliberately contained CRLF was committed with LF, and only a `.gitattributes` rule fixed it.

The first grading of the translations also taught me something. The automated reviewer claimed the Java version printed `error_rate` as a string. The claim was wrong, because my tests proved the output was a number, but the helper function returned a `String`, and that made the code look suspicious. I changed it to return a numeric type, which is clearer. Code is read by people and tools, so clarity matters even when the output is already correct.

The benchmark was humbling. JavaScript was fastest at 1.59 seconds for a million lines, Python used the least memory at 31 MB, and my unoptimized Java version was slow and memory-hungry. I could not explain every difference, since I did not profile or tune anything, so the report states the limits instead of inventing reasons.

Next time I would write the shared tests and the cross-language runner before the second translation, and I would test on a clean checkout earlier. I would also profile the Java version before drawing any conclusion about the language.
