# Performance Report - Log Analyzer (Python, JavaScript, Java)

All numbers below were measured on 2026-11-09 with the scripts in `benchmarks/`. Nothing here is estimated.

## Setup
| Item | Value |
|---|---|
| Machine | Intel Core i7-13650HX (14 cores / 20 threads), 23.7 GB RAM, Windows 11 Pro 10.0.26300 |
| Python | 3.13.5 |
| Node.js | v24.18.0 |
| Java | OpenJDK 21.0.10 (default JVM flags, no tuning) |
| Input | `build/bench_1m.log`: 1,000,000 lines, 78.3 MB, generated by `benchmarks/generate_log.py` (seed 2026): about 3% malformed lines, 0.5% blank lines, 50,000 distinct IPs |
| Output | 995,058 non-blank lines, 964,968 valid, 30,090 malformed, 50,000 unique IPs |
| Programs | `implementations/python/log_analyzer.py`, `implementations/javascript/log_analyzer.js`, `implementations/java/LogAnalyzer.java` |

## Method
Run `python benchmarks/generate_log.py build/bench_1m.log 1000000` and then `python benchmarks/run_benchmark.py build/bench_1m.log 5`.
- Each measurement is a fresh process running the command-line program, so the time includes interpreter or VM start-up (and JIT warm-up for Java).
- One untimed warm-up run per language, then **5 timed runs**.
- **Runtime**: wall-clock time from spawn to exit (`time.perf_counter`).
- **Memory**: the process's **peak working set** (Windows `GetProcessMemoryInfo`, `PeakWorkingSetSize`). It includes the runtime itself, not just program data.
- The harness hashes every run's output and checks that all three languages print byte-identical results (they did: `identical_output_across_languages: true`).

## Results (1,000,000 lines)
| Language | Runtime median (s) | Runtime range (s) | Peak memory median (MB) | Memory range (MB) |
|---|---|---|---|---|
| Python | 3.95 | 3.89 - 4.15 | 31 | 31 - 31 |
| JavaScript | 1.59 | 1.56 - 1.62 | 230 | 229 - 230 |
| Java | 4.02 | 3.97 - 4.07 | 308 | 308 - 387 |

Individual runs (s): Python 3.95, 3.98, 4.15, 3.89, 3.94; JavaScript 1.59, 1.60, 1.62, 1.56, 1.58; Java 4.07, 4.03, 4.02, 3.97, 4.01.
Individual peak memory (MB): Python 31 x5; JavaScript 230, 229, 230, 230, 229; Java 308, 308, 308, 311, 387.

## Start-up baseline (6-line file, 5 runs)
| Language | Runtime (s) | Peak memory (MB) |
|---|---|---|
| Python | 0.03 | 13 |
| JavaScript | 0.04 | 49 |
| Java | 0.06 | 42 |

Start-up is tiny compared with the 1M-line times, so the differences above come from processing the data, not from launching the runtimes.

## What the numbers show
- **JavaScript was the fastest** on this input (about 2.5x faster than Python and Java).
- **Python used by far the least memory** (31 MB vs 230 MB and 308 MB). All three programs stream the file instead of loading it whole, and the start-up baseline above (13 to 49 MB) explains only part of the difference.
- **Java and Python took about the same time**, around 4 seconds.

## What they do not show (limits)
- This is **one machine, one input shape and 5 runs per language**; the ranges are narrow, but it is not a statistical study and other machines or inputs may rank differently.
- Peak **working set** is not the same as the memory the program needs. The JVM sizes its heap by default policy (the Java peak is likely about heap policy, not the real data), and V8 can let garbage build up before collecting. I did not run experiments with `-Xmx`, `--max-old-space-size` or a tracing profiler, so I make no claim about the cause of the memory differences.
- The Java version is a straightforward translation and **not optimized**: it reads one byte at a time into a `ByteArrayOutputStream` and creates a `String` for every line. I suspect this explains the runtime gap, but I did not test that; faster I/O could change the ranking.
- Python's number reflects CPython with the `re` module; no PyPy or compiled extensions were tried.
- Results measure these three implementations, not the languages in general.

## Reproduce
```sh
python benchmarks/generate_log.py build/bench_1m.log 1000000
python benchmarks/run_benchmark.py build/bench_1m.log 5
```
Requires Python 3, Node.js and a JDK. The memory measurement was verified on Windows only; the script includes a Linux/macOS path (`ru_maxrss`) that has not been tested.
